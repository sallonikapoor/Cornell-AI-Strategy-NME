WEEK 06 / DATA CLEANING & VALIDATION

Data cleaning and validation.

Find the problems in a dataset, fix them with documented decisions, and add validation so your project rejects bad data.

About 60 minutesLaptop requiredLive or self-pacedPortfolio piece #4

This week your project starts working with data. Most data has problems when it arrives: dates in different formats, the same category spelled several ways, repeated rows, and extra rows like totals. If a project uses that data without checking it, its results are wrong, and nothing warns you.

In this lesson you will:

  • Create a practice dataset for your project with problems built in.
  • Find each problem and record it by row number.
  • Decide how to handle each problem and create a clean copy of the file.
  • Add an import feature that checks every row and rejects the ones that break your rules.
  • Document what you did in your README and publish the update.

Why data quality matters →
01 / WHY DATA QUALITY MATTERS

Why data quality matters.

Bad data rarely causes an error message. It causes wrong results that look correct.

Two well-known examples:

  • Mars Climate Orbiter (1999). NASA lost a $125 million spacecraft because one team's software produced measurements in English units and another team's software expected metric units. The numbers looked reasonable, but they meant something different from what the receiving system assumed. Read more
  • Gene names in Excel (2020). Scientists renamed 27 human genes, including SEPT1 and MARCH1, because Excel automatically converted those names into dates in research spreadsheets. Read more

The same kinds of problems affect small projects. A spending total is wrong because one amount includes a dollar sign the code can't read. A deadline is missing because its date was written "Oct 4." A category appears twice because one row says "Food" and another says "food."

Common data problems

Missing values.

A required cell is blank, such as an expense with no amount.

Inconsistent formats.

The same type of value is written in different ways, such as 2026-10-02, 10/02/2026, and Oct 2 2026.

Inconsistent labels.

One category is spelled several ways, such as Food, food, and FOOD (with a trailing space).

Duplicates.

The same row appears more than once. Sometimes this is an error, and sometimes it reflects two real events.

Impossible or unusual values.

A value that can't be right, such as a date in the future, or one that is allowed but unusual, such as an amount ten times larger than the rest.

Rows that aren't data.

Totals, notes, or repeated headers mixed in with the records.

Cleaning and validation

Cleaning

corrects one specific file. You review each problem and decide how to handle it.

Validation

checks every file your project receives in the future. Each cleaning decision becomes a rule, and the project applies those rules automatically when data is imported.

This lesson covers both: you clean one file by hand, then add validation so the same problems are caught automatically.

    Inspect the data

- Any rows that aren't data at all, like totals or notes

Clean the data →
04 / DECIDE AND CLEAN

Clean the data.

Decide how to handle each problem, record the decision, and create a clean copy of the file.

Ways to handle a problem

Fix it.

The correct value is clear. Example: change Oct 4 2026 to 2026-10-04.

Remove it.

The row is not a valid record. Example: a totals row, or a duplicate created by an export error.

Keep it and flag it.

The value is allowed but unusual, so someone should confirm it. Example: a $1,200 concert ticket.

Set it aside for review.

The correct value can't be determined from the file. Example: a date in 2027 may be a typo for 2026, but that can't be confirmed.

Two rules apply to every decision:

  • Don't guess. If a fix would require inventing a value, set the row aside for review instead.
  • Account for every row. Rows in the clean file plus rows removed or set aside must equal the rows in the raw file.

Add validation →
05 / VALIDATE

Add validation.

Turn your cleaning decisions into rules, and have your project check every imported row against them.

Write validation rules

Most decisions in your problem log can become a rule: a check that each row either passes or fails. Write each rule specifically enough that, when a row fails, the message tells the person what to fix.

Rules for the spending tracker:

  1. Date is written YYYY-MM-DD, is a real date, and isn't in the future.
  2. Description isn't blank.
  3. Amount is a plain number above zero, with no symbols.
  4. Category is exactly Food, Transport, Fun, or Other.

One warning, which imports the row but labels it:

  • A row that exactly matches an earlier row is marked "possible duplicate." It isn't rejected, because identical purchases can be real.

Not every decision becomes a rule. The $1,200 concert ticket passes all four rules, because large purchases are allowed. Checks like that remain a person's responsibility.

Common problems →
07 / COMMON PROBLEMS

Common problems and fixes.

The generated data doesn't fit my project. +

Ask again with more detail: "My project tracks [what]. The columns should be [list them]." If your project doesn't obviously use a table, ask ChatGPT what kind of list it could import, such as past workouts, assignments, or recipes.

Codex changed raw.csv. +

Discard the change in GitHub Desktop (right-click the file, then Discard changes). Then remind Codex in your next message: "Never edit data/raw.csv. Write all changes to data/clean.csv."

My row counts don't add up. +

Ask Codex: "List every row number from raw.csv and say whether it's in clean.csv, removed, or set aside." The missing row is usually a blank line or the header being counted.

The import button does nothing. +

Open the page, then open your browser's developer console (right-click the page, choose Inspect, then Console), try the import again, and screenshot any red error. Paste the screenshot into the ChatGPT app and ask what to tell Codex.

raw.csv imports with no rejections. +

Your rules aren't being applied, or they're too loose. Paste your rules and Codex's import code into the ChatGPT app and ask: "Which of these rules would reject a date written as 10/02/2026? Show me where in the code."

My spreadsheet app changed the data. +

Spreadsheet apps can convert values into dates or remove leading zeros, as happened with the gene names. You can view the file in a spreadsheet app, but don't save it there. Make all edits through Codex.
