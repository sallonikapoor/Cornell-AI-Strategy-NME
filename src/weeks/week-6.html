WEEK 06 / DATA CLEANING & VALIDATION

Data cleaning and validation.

Find the problems in a dataset, fix them with documented decisions, and add validation so your project rejects bad data.

About 60 minutesLaptop requiredLive or self-pacedPortfolio piece #4

This week your project starts working with data. Most data has problems when it arrives: dates in different formats, the same category spelled several ways, repeated rows, and extra rows like totals. If a project uses that data without checking it, its results are wrong, and nothing warns you.

Why data quality matters →
01 / WHY DATA QUALITY MATTERS

Why data quality matters.

Bad data rarely causes an error message. It causes wrong results that look correct.

Two well-known examples:

  • Mars Climate Orbiter (1999). NASA lost a $125 million spacecraft because one team's software produced measurements in English units and another team's software expected metric units. The numbers looked reasonable, but they meant something different from what the receiving system assumed. Read more
  • Gene names in Excel (2020). Scientists renamed 27 human genes, including SEPT1 and MARCH1, because Excel automatically converted those names into dates in research spreadsheets. Read more

The same kinds of problems affect small projects. A spending total is wrong because one amount includes a dollar sign the code can't read. A deadline is missing because its date was written "Oct 4." A category appears twice because one row says "Food" and another says "food."

Common data problems

Missing values.

A required cell is blank, such as an expense with no amount.

Inconsistent formats.

The same type of value is written in different ways, such as 2026-10-02, 10/02/2026, and Oct 2 2026.

Inconsistent labels.

One category is spelled several ways, such as Food, food, and FOOD (with a trailing space).

Duplicates.

The same row appears more than once. Sometimes this is an error, and sometimes it reflects two real events.

Impossible or unusual values.

A value that can't be right, such as a date in the future, or one that is allowed but unusual, such as an amount ten times larger than the rest.

Rows that aren't data.

Totals, notes, or repeated headers mixed in with the records.

How a computer reads a CSV

A CSV is a plain text file. Each line is a row, and commas separate the values in it. The first line is the header, which names the columns. If you open raw.csv in a text editor, that's all you'll see: no formatting, no cell types, just text.

When code reads the file, every value arrives as text. 12.50 is five characters, not a number, until the code converts it. Most data problems show up during that conversion:

In the fileWhat the code needsWhat goes wrong
$1,200.00A number$ and , aren't digits, so the conversion fails and the total becomes NaN ("not a number").
10/02/2026A dateIt could mean October 2 or February 10. The code has to pick one.
food The category FoodTo a computer, food and Food are different text, so they become two categories.
TOTAL,,1787.70One expenseNothing marks it as a summary, so it's added to the total again.

This is why the clean file uses one format for each type. Dates are written YYYY-MM-DD because that format has only one meaning, and it sorts correctly as text: 2026-09-30 comes before 2026-10-02.

Cleaning and validation

Cleaning

Fixes one specific file. You review each problem and decide how to handle it.

Validation

Checks every file your project receives from now on. Each cleaning decision becomes a rule, and the project applies those rules automatically when data is imported.

This lesson covers both. You write code that cleans one file, then add validation so the same problems are caught in every file after it.

Clean the data →
04 / DECIDE AND CLEAN

Clean the data.

Decide how to handle each problem, record the decision, and create a clean copy of the file.

Ways to handle a problem

Fix it.

The correct value is clear. Example: change Oct 4 2026 to 2026-10-04.

Remove it.

The row is not a valid record. Example: a totals row, or a duplicate created by an export error.

Keep it and flag it.

The value is allowed but unusual, so someone should confirm it. Example: a $1,200 concert ticket.

Set it aside for review.

The correct value can't be determined from the file. Example: a date in 2027 may be a typo for 2026, but that can't be confirmed.

Two rules apply to every decision:

  • Don't guess. If a fix would require inventing a value, set the row aside for review instead.
  • Account for every row. Rows in the clean file plus rows removed or set aside must equal the rows in the raw file.

ProblemRowsDecision
Dates written three ways4, 6, 10, 18, 22Fixed: rewrote them as YYYY-MM-DD. Slash dates use US month/day order. Row 22 (10/18/2026) proves it, since there's no month 18.

Most decisions are rules that apply to every row, like "match categories ignoring case." Some aren't. The Uber rides and the coffees are both exact duplicates, but only one pair is a mistake, and only a person reading the descriptions can tell which. These are manual decisions. Your cleaning code lists them by row number, with a reason, so anyone can see exactly what was decided and why.

The same care applies to dates. 10/02/2026 could mean October 2 or February 10. This file is only safe to convert because its other dates prove it uses US month/day order. With an unfamiliar file, confirm the format before converting anything.

Write the cleaning code

You could fix this file by hand in a few minutes. Writing code takes a little longer, but it has three advantages:

  • You can rerun it. If the raw file changes, run the code again instead of redoing every fix.
  • Anyone can check it. The code shows exactly what was changed and why, row by row.
  • It carries over. The same rules become your validation in the next section.

Data teams work the same way. A step-by-step program that loads, cleans, and checks data each time new data arrives is called a pipeline. What you build tonight is a small one.

Instead of having Codex edit the file, have it write code that does the cleaning. Code can be rerun, gives the same result every time, and shows exactly what changed. The cleaning code works in three stages:

Normalize.

Rewrite each value into one standard form: dates as YYYY-MM-DD, amounts as whole cents, categories from the allowed list.

Decide.

Apply your decisions: remove rows, set rows aside for review, or keep them.

Check.

Confirm every raw row ended up in exactly one place: clean, removed, or set aside.

Why amounts are stored in cents.

Computers can't store most decimals exactly. Open your browser's console (right-click any page, choose Inspect, then Console) and type 0.1 + 0.2. The answer is 0.30000000000000004. Storing $12.50 as 1250 cents avoids the problem.

Add validation →
05 / VALIDATE

Add validation.

Turn your cleaning decisions into rules, and have your project check every imported row against them.

Validation runs at the moment data enters your project, before anything is saved or added to a total. If every row is checked at that point, the rest of your code can trust what it receives and doesn't need its own checks. Sign-up forms work the same way when they reject an email address with no @ before you can submit.

Write a data contract

A data contract says what every column must contain. It turns your decisions into rules code can enforce, and it lives in one place, so changing a rule there changes what gets rejected everywhere.

The spending tracker's contract:

ColumnTypeRequiredRule
DatedateYesWritten YYYY-MM-DD, a real date, and not after today
DescriptiontextYesNot blank
AmountmoneyYesA plain number above zero, with at most two decimal places and no symbols
CategorychoiceYesExactly Food, Transport, Fun, or Other

One warning, which loads the row but labels it: a row that exactly matches an earlier row is marked as a possible duplicate, because identical purchases can be real.

Not everything becomes a rule. The $1,200 concert ticket passes the contract, because large purchases are allowed. A person still has to catch those.

Why the tests pass in today's date.

"Not after today" gives a different answer depending on when it runs. Row 15 is dated October 12, 2027, so after that day it would stop failing. Passing today's date into the validator, instead of reading the clock, lets the tests use a fixed date and give the same result every day.

Common problems →
07 / COMMON PROBLEMS

Common problems and fixes.

The generated data doesn't fit my project. +

Ask again with more detail: "My project tracks [what]. The columns should be [list them]." If your project doesn't obviously use a table, ask ChatGPT what kind of list it could import, such as past workouts, assignments, or recipes.

Codex changed raw.csv. +

Discard the change in GitHub Desktop (right-click the file, then Discard changes). Then remind Codex in your next message: "Never edit data/raw.csv. Write all changes to data/clean.csv."

My row counts don't add up. +

Ask Codex: "List every row number from raw.csv and say whether it's in clean.csv, removed, or set aside." The missing row is usually a blank line or the header being counted.

The import button does nothing. +

Open the page, then open your browser's developer console (right-click the page, choose Inspect, then Console), try the import again, and screenshot any red error. Paste the screenshot into the ChatGPT app and ask what to tell Codex.

raw.csv imports with no rejections. +

Your rules aren't being applied, or they're too loose. Paste your rules and Codex's import code into the ChatGPT app and ask: "Which of these rules would reject a date written as 10/02/2026? Show me where in the code."

My spreadsheet app changed the data. +

Spreadsheet apps can convert values into dates or remove leading zeros, as happened with the gene names. You can view the file in a spreadsheet app, but don't save it there. Make all edits through Codex.

My CSV has rows with too many columns. +

A value with a comma that isn't in quotes, like $1,200.00, gets split into two columns. Ask ChatGPT to regenerate the file with every value that contains a comma in double quotes, or record it as a problem and set those rows aside for review.

clean.html or tests.html shows nothing. +

Open the browser console (right-click the page, choose Inspect, then Console), screenshot any red error, and paste it into the ChatGPT app. Ask what to tell Codex.

Codex changed a test to make it pass. +

Discard that change in GitHub Desktop: right-click the file, then Discard changes. Then tell Codex: "Don't change the tests. Change the code until the tests pass."
