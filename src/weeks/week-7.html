APIs and automation.

Learn how software asks other software for data, how to read what comes back, and when an API is the right tool.

What an API is →
01 / WHAT AN API IS

What an API is.

An API is a set of rules for how one program asks another program for data or for an action.

API stands for application programming interface. People use an app through its interface: buttons, forms, and screens. Programs use another program through its API: a fixed list of requests they can send and the responses they'll get back.

Most APIs you'll use work over the web. One program, the client, sends a request to an address on the internet. Another program, the server, does the work and sends back a response. In this lesson the client is your web page.

Request. Your code sends a message to a web address saying what it wants.
Processing. The server checks the request, then looks up the data or does the action.
Response. The server sends back a status code and, usually, data.
Use. Your code reads the response and updates the page.

What an API gives you

Data.

Information someone else collects and keeps current: weather, exchange rates, sports scores, flight times.

Actions.

Work that takes a large system to do: charging a card, sending an email or text, translating text.

Access to another app.

Reading or changing your data in apps like Google Calendar, Slack, or GitHub.

AI models.

Sending text to a model like GPT or Claude and getting its response back. Most AI features in apps are built this way.

An API is a contract

Every API has documentation, usually called the docs. The docs list what you can ask for and what you'll get back: the addresses, the options each one accepts, and the shape of each response. As long as both sides follow the docs, the client doesn't need to know how the server works inside, and the server can change its internals without breaking any client.

You've already used several APIs.

Codex sends your prompts to OpenAI's servers through an API. GitHub Desktop uses GitHub's API to sign you in and list your repositories. When your site deploys, the last step calls the GitHub Pages API.

The parts of a request →
02 / THE PARTS OF A REQUEST

The parts of a request.

A request says where it's going, what kind of action it is, and any details the server needs.

The address

Here's a real request to Open-Meteo, a free weather API. It asks for the current temperature in Ithaca, in Fahrenheit:

Request URL

https://api.open-meteo.com/v1/forecast?latitude=42.44&longitude=-76.50&current=temperature_2m&temperature_unit=fahrenheit

PartIn this requestWhat it does
Protocolhttps://How the request travels. The s means it's encrypted.
Hostapi.open-meteo.comThe server that receives the request.
Path/v1/forecastWhich part of the API you're calling. A path like this is called an endpoint. v1 is the API's version.
Query string?latitude=42.44&longitude=-76.50&...Options for the request, written as name=value pairs. ? starts the list and & separates each pair.
Parameterslatitude, longitude, current, temperature_unitThe option names. The docs list which ones each endpoint accepts.

Try it. Open the request in your browser. The browser sends the request and shows the raw response. Then change latitude and longitude to another city's and load it again. The endpoint is the same, the parameters are different, and so is the data.

The method

Every request has a method, which says what kind of action it is. Opening a link in your browser always sends a GET.

MethodWhat it doesExample
GETReads data. Changes nothing.Get the forecast.
POSTCreates something, or sends data to be processed.Send a message to an AI model. Submit a payment.
PUT or PATCHUpdates something that exists. PUT replaces it, and PATCH changes part of it.Change the time of a calendar event.
DELETERemoves something.Delete a calendar event.

This week you'll only use GET.

Headers and body

A request can also carry headers and a body.

Headers are labels with extra information, written as name: value. Two you'll see often:

  • Content-Type: application/json says the body is written in JSON.
  • Authorization: Bearer [key] says who is sending the request. Section 05 covers keys.

The body is the data being sent. It's used with POST, PUT, and PATCH. A GET request has no body, so everything it needs goes in the URL.

Reading the response →
03 / READING THE RESPONSE

Reading the response.

A response has a status code that says what happened and a body that holds the data.

Status codes

The status code is a three-digit number. Its first digit gives the category: 2 means it worked, 4 means something was wrong with the request, and 5 means something went wrong on the server.

CodeMeaningWhat to do
200 OKIt worked. The data is in the body.Use the data.
400 Bad RequestThe server couldn't read the request, often because a parameter is missing or misspelled.Compare the request with the docs.
401 UnauthorizedThe key is missing or wrong.Check the key.
403 ForbiddenThe key works but isn't allowed to do this.Check your plan or permissions.
404 Not FoundNothing exists at that address.Check the path for typos.
429 Too Many RequestsYou've passed the rate limit.Wait, then send fewer requests.
500 Internal Server ErrorSomething broke on the server.Try again later. It isn't caused by your code.
503 Service UnavailableThe server is down or overloaded.Try again later, and show a message until then.

A failed request can still have a body. Many APIs use it to explain what went wrong.

JSON

Most APIs send data as JSON (JavaScript Object Notation): plain text in a format code can read directly. The Ithaca request returns a response like this one, shortened:

Response body

{
  "latitude": 42.43,
  "longitude": -76.5,
  "timezone": "GMT",
  "current_units": {
    "time": "iso8601",
    "temperature_2m": "°F"
  },
  "current": {
    "time": "2026-11-11T19:00",
    "temperature_2m": 41.2
  }
}

PartExampleWhat it is
Object{ ... }A group of named values, inside curly braces.
Key"temperature_2m"The name of a value. Always in double quotes.
Value41.2The data. It can be text ("°F"), a number (41.2), true or false, null for empty, an object, or a list.
Array[ ... ]An ordered list of values, inside square brackets.
Nesting"current": { ... }An object inside another object.

To reach a value, follow the keys from the outside in. In code, the temperature is data.current.temperature_2m: start at the whole response (data), open current, then read temperature_2m. In an array, positions start at 0, so items[0] is the first item.

Read the whole response before deciding what to use. This one also tells you the unit (°F) and the time. The time is in GMT, not Ithaca time, unless you add &timezone=auto to the request.

Calling an API from code →






04 / CALLING AN API FROM CODE


Calling an API from code.


In a web page, JavaScript sends requests with fetch. Your code has to handle the response, and the cases where no response arrives.


This is the kind of code Codex writes for a GET request, shortened to the parts that matter:


Get the temperature
async function getTemperature() {
  const url = "https://api.open-meteo.com/v1/forecast?latitude=42.44&longitude=-76.50&current=temperature_2m&temperature_unit=fahrenheit";

  const response = await fetch(url, { signal: AbortSignal.timeout(8000) });

  if (!response.ok) {
    throw new Error("The weather service answered " + response.status);
  }

  const data = await response.json();
  return data.current.temperature_2m;
}


CodeWhat it does
async functionMarks a function that waits on something. The rest of the page keeps working while it waits.
fetch(url, ...)Sends the request.
awaitWaits for the result before running the next line.
AbortSignal.timeout(8000)Cancels the request after 8 seconds (8,000 milliseconds) instead of waiting forever.
response.oktrue for status codes 200 to 299. Anything else means the request failed.
throw new Error(...)Stops the function and reports the failure to the code that called it.
response.json()Reads the body and turns the JSON text into an object your code can use.
data.current.temperature_2mFollows the keys to the one value you need.


Requests take time


A request can take a few milliseconds or several seconds, so the page needs three states:


Loading.
Show that something is happening, such as "Loading rates…" Disable the button so it can't be clicked twice.
Success.
Show the data.
Failure.
Show a short message that says what didn't load, and keep the rest of the page working.


Four ways a request fails


FailureWhat your code seesWhat to do
No connection, or the server is downfetch throws an error, and there's no responseCatch the error and show the failure message.
Too slowThe timeout cancels the request, and fetch throwsSame as above. Let the person try again.
Error statusresponse.ok is falseShow the failure message. Log the status code so you can debug it.
Wrong dataStatus 200, but a field is missing, empty, or the wrong typeCheck each field before you use it.


The last row is the easiest to miss. A 200 only means the server answered. It doesn't mean the data is what you expect. Check the response like any other data entering your project: is each field there, and is it the right type?


Check the response
function checkResponse(data) {
  const temp = data?.current?.temperature_2m;
  if (typeof temp !== "number") {
    return { ok: false, error: "The response had no temperature." };
  }
  return { ok: true, value: temp };
}


?. reads a key only if the object before it exists. If current is missing, temp becomes undefined instead of crashing the page, and the check returns an error.


Save the last good response


Many apps save their last successful response in the browser (in localStorage), along with the time it was fetched. If the next request fails, the page shows the saved data and says how old it is, such as "Last updated Nov 10, 9:00 PM." This is called caching. It also lets the page skip a request when the saved data is recent enough.


Keys, limits, and CORS →






05 / KEYS, LIMITS, AND CORS


Keys, limits, and CORS.


Three things decide which APIs your site can use: whether an API needs a secret key, how many requests it allows, and whether it accepts requests from a browser.


API keys


Many APIs need a key: a long string that identifies who's sending each request. The API uses it to count your requests, apply your plan's limits, and bill you if the API charges. A key is usually sent in a header (Authorization: Bearer [key]) or as a parameter (?key=...).


No key.
Anyone can call it. Works on a static site. Examples: Open-Meteo, Frankfurter.
Publishable key.
Meant to be visible, and locked to your site's address in the provider's settings. Examples: a Google Maps JavaScript key, a Stripe publishable key.
Secret key.
Must stay on a server. Examples: OpenAI, Anthropic, and Stripe secret keys.


A secret key can't go in your site.
Your site is static: every file, including script.js, is downloaded to each visitor's browser, where anyone can read it. Public repositories are also scanned for leaked keys, by GitHub and by people who want to use them. If a secret key is ever committed, treat it as public: revoke it in the provider's dashboard and create a new one. Deleting the commit isn't enough, because the history keeps it.


APIs with secret keys, including AI model APIs, are called from a backend: a server you control that holds the key, calls the API, and passes the result to your page. That's outside this week's scope. This week, use an API that needs no key.


Rate limits


Most APIs cap how many requests you can send per minute, hour, or day. Past the limit, you get 429 Too Many Requests. Two habits keep you under it:


  • Request only when needed: when the page loads or when someone clicks, never in a loop.
  • Reuse a saved response while it's still current. Frankfurter's exchange rates update once each working day, so requesting them every few seconds gets you nothing new.


CORS


Browsers block a page from reading a response from another site unless that site allows it. This rule is called CORS (cross-origin resource sharing). A server allows it by sending a header, Access-Control-Allow-Origin, with its response. If the header is missing, the request may still reach the server, but your code can't read the answer, and the browser's console shows an error that mentions "blocked by CORS policy."


You can't fix CORS from your page. It's the API's decision. An API that doesn't allow browser requests is meant to be called from a server, so pick a different one. Before you commit to an API, check its docs for "CORS" or "browser," or send one request from your page.


Terms of use


Free APIs come with conditions, such as credit to the provider, non-commercial use only, or a daily cap. Open-Meteo, for example, is free for non-commercial use. Read the terms before you build, and link the API's docs in your README.


When to use an API →






06 / WHEN TO USE AN API


When to use an API.


Use an API when the data or the work lives somewhere else and keeps changing. If it doesn't, a file or your own code is simpler.


SituationUseWhy
The data changes often: weather, prices, exchange rates, schedulesAn APIA saved file would go out of date.
Someone else keeps the data currentAn APIOtherwise you'd have to collect it yourself.
You need work that takes a large system: payments, maps, email, an AI modelAn APIYou can't reasonably build these yourself.
Your data lives in another app: a calendar, Slack, a CRMThat app's APIIt's the supported way to read and change that data.
The data rarely changes: a list of states, your project's categoriesA file in your projectIt's faster, works offline, and has nothing that can fail.
You can calculate it yourself: a total, the days between two datesYour own codeNo request, no wait, and no limit.
The API needs a secret key, and your project has no serverNot yetThe key would be public.
You'd send personal data to a service you haven't checkedDon'tRead its privacy terms first.


Before you choose an API


  • Does it have the data I need? Open one response and check the fields.
  • Does it need a key? If so, is the key safe to make public?
  • Does it accept requests from a browser?
  • What are its limits, and will my project stay under them?
  • What will my project do if it goes down?
  • What do its terms allow?


APIs in client work


In client projects, an AI feature is usually an API call: the client's app sends text and instructions to a model provider and gets a response back. The same questions apply, plus a few more: who holds the key, what each request costs, how many requests the feature will send, what data leaves the client's systems, and what the app does when the provider is slow or down.


Automation →






07 / AUTOMATION


Automation.


Automation means a step runs without anyone starting it by hand. Most automations work by calling APIs.


An automation has a trigger and an action. The trigger decides when it runs. The action is what it does, which is often one or more API requests.


Schedule.
Runs at set times, such as every day at 8 AM. Scheduled jobs are often called cron jobs. Example: fetch the day's exchange rates and save them.
Event.
Runs when something happens, such as a push or a form submission. Example: your site's deploy. Every push to main starts a GitHub Actions workflow that builds and publishes the site.
Webhook.
Another service sends a request to your server when something happens. It's an API call in reverse: instead of your code asking "anything new?", the service tells you. Example: a payment provider notifying a store's server that a payment went through.


Tools like GitHub Actions, Zapier, and Make connect triggers to actions without running your own server.


An automation can fail with no one watching, so it needs a way to report failures, such as an email or a log. GitHub Actions emails you when a workflow fails.

Common problems →






08 / COMMON PROBLEMS


Common problems and fixes.


The console says "blocked by CORS policy." +
The API doesn't allow requests from a browser, and nothing in your code can change that. Choose a different API from the list in section 09.
I get 401 or 403. +
The API needs a key. Don't put one in your site. Choose an API that needs no key.
I get 429. +
Your page is sending too many requests. Ask Codex: "Find every place my code calls the API, and make sure it only runs on page load or when the button is clicked."
The request works, but the page shows "undefined." +
The code is reading a key that isn't in the response, or the path to it is wrong. Open the request in your browser, find the value, and compare its path with the one in your code. Keys are case-sensitive.
The page goes blank when the API fails. +
The error isn't being caught. Ask Codex: "When the API request fails for any reason, show my failure message and keep the rest of the page working. Don't let the error stop the page."
It works on my laptop but not on my live site. +
Check that the request URL starts with https://. A page served over https can't request an http:// address. If it still fails, open the console on the live site and look for a red error.
I can't find an API that fits my project. +
Ask ChatGPT: "My project is [your project sentence]. Suggest three free APIs that need no key and allow requests from a browser, with a docs link for each." Then check each one against the questions in section 06.


Check your understanding


A request returns 200, but your page shows "undefined." Is the API broken? +
No. The request worked. Your code is reading the wrong path. Compare the path in your code with the JSON.
Why can't an OpenAI key go in script.js? +
Every visitor downloads script.js and can read the key. Anyone who copies it can send requests that you pay for. Secret keys belong on a server.
A request works in the address bar but fails from your page with a CORS error. Why? +
The address bar isn't subject to CORS, but your page is. The server doesn't allow other sites' pages to read its responses.
Exchange rates update once a day. How often should your page request them? +
At most once per visit, and less if you save the last response. Extra requests slow the page down and count against the limit.
You get a 400 and then a 503. Which one comes from your request? +
The 400. It means the request itself was wrong. A 503 means the server is unavailable, so try again later.
