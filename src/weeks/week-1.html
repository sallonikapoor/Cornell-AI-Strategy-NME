01 / HOW LLMS WORK

A mental model.
Before the actual model.

Training is where a model learns patterns. Inference is where it uses them.

TRAINING

Labeled emails → learned patterns

Classic machine learning learns from examples. Show it thousands of emails marked "spam" or "not spam," and it figures out what spam tends to look like.

INFERENCE

New email → prediction

Give the trained model an email it has never seen, and it makes a call: "Spam (94%)."

An LLM works on the same basic idea at a much bigger scale. It's trained on an enormous amount of text to predict what comes next.

How models learn from data, including neural networks and the difference between classification and regression, is covered in Week 4.

The right tool depends on the task

LLMs aren't always the answer. If a task is narrow and repetitive, or you have lots of labeled examples, a simple rule or a classic ML model is often faster, cheaper, and more consistent. And anything that needs exact math should happen in code.

INSIDE THE LOOP

One token at a time.

ILLUSTRATIVE DEMO

An LLM breaks text into small pieces called tokens. A token can be a whole word, part of a word, or punctuation. The model predicts the next token, adds it to the text, and repeats.

ThecapitalofFranceis?

Context is ready. What comes next?

This is a simplified animation. Real token boundaries vary by model.

At each step, the model scores every possible next token by how likely it is. Then it picks one. It doesn't always pick the top choice, which is part of why you can get different answers to the same question. Whatever it picks becomes part of the text, so one early choice can steer the whole rest of the answer.

The model was trained to write text that sounds like it belongs. That skill gets you a lot: useful explanations, good drafts, often correct answers. But writing a likely-sounding sentence is a different job from checking a source, doing arithmetic, or confirming a payment. Some assistants can call tools for those jobs. When they don't, nothing inside the model is checking the work.

It generates plausible text.
Plausible ≠ true.

What the model sees

Normal sentences, ID numbers, and single words all get split up differently.

The capital of France is ParisAcme Corporation Invoice #INV-2024-00817strawberry

Look at how the invoice ID breaks into several chunks, and how even a simple word can get split into pieces. The model doesn't see individual characters the way you do, so it can't reliably count or copy them one by one. When an exact string matters, like an invoice number, keep the original and let code compare it. More on tokens

Bonus: Exact Strings

Try this now, while tokens are fresh in your mind. Then check the result against the original ID.

How many times does the digit 0 appear in INV-2024-00817? Then write the ID backwards, character by character.

What to look for +

Answer: 3 zeros. Reversed: 71800-4202-VNI.

Watch for a wrong count or scrambled characters. Plenty of models get this right, especially if they use a tool. But if a workflow depends on IDs, check them in code anyway.

Model vs. assistant

Chat products like ChatGPT and Claude wrap a model in extra layers: instructions from the company, tools like code execution or web search, and sometimes memory. So when an assistant gets a calculation right, it may have used a tool rather than doing the math itself. In Weeks 3 and 7, you'll work with models more directly and control these layers yourself.

So don't assume a model knows your client's data or anything that happened recently. If it needs to know something, you have to put it in front of it, either by pasting it in or by connecting a tool that can look it up.

Instruction tuning and good prompts make a model easier to work with. They don't make it fact-check itself. And more context only helps if that context is relevant and correct.

That's why an answer can sound completely right and still be wrong. Next, the four ways this usually shows up, and how to catch each one.

02 / FAILURES & DEFENSES

Find the failure.
Design the defense.

You can predict how these models fail. That means you can plan where to check their work.

Models don't fail every time, and newer ones fail less. But on client work, "usually right" isn't good enough. What matters is what happens on the day it's wrong, and whether your workflow catches the mistake before anyone acts on it.

01HallucinationConfident, fluent, and wrong+

What went wrong

You ask a model to summarize a vendor agreement. It tells you the contract allows cancellation with 30 days' notice. That sounds completely normal, so it goes straight into the client memo. The problem: the excerpt you gave it doesn't mention cancellation at all.

Why it happens

The model's goal is to write something that sounds right. So what happens when it doesn't know the answer? It writes something that sounds right anyway, sometimes with a real-looking citation attached. Training that rewards giving an answer over admitting "I don't know" makes this worse.

How to catch it

Make the model point to the exact passage behind every important claim, and give it permission to say "not found." Then have someone open that passage and confirm it actually says what the model claims. A citation only tells you where to look.

Week 8 · grounding and citations
02InconsistencySame task, different judgments+

What went wrong

You run the same deduction note through a model twice. The note mentions crushed goods and a short shipment. The first run labels it DAMAGE. The second labels it SHORTAGE. If each label sends the case to a different team, the same claim gets handled two different ways.

Why it happens

Remember that the model doesn't always pick its top choice. Run the same prompt twice and it can take a different path, and one different word early on can change where the answer ends up. Vague instructions make this worse, because the model has to guess what you meant.

How to catch it

Define every category clearly, show examples of the tricky cases, and say what to do when information is missing. Before you trust it, run it on 20 or 30 real examples. If a case is unclear or expensive to get wrong, send it to a person. And keep in mind that getting the same answer every time doesn't mean it's the right answer.

Weeks 3, 9 · clear prompts and review
03Unreliable mathA generated total needs a calculation+

What went wrong

An invoice has 20 line items. The model gives you a total that looks reasonable but is off by $90. When you ask "are you sure?", it confidently repeats the same wrong number.

Why it happens

When a model writes out a number, it's predicting digits from patterns rather than calculating. It gets a lot of arithmetic right. But in a long sum, one small slip early on throws off everything after it, and the model doesn't go back and check. Assistants that can run code are different: when they actually use that tool, a real calculation happens.

How to catch it

Have code do the math, using exact decimal amounts (or whole cents) so nothing gets rounded. Compare the code's total to the invoice total, and send any mismatch to review. Check the inputs too. A perfect sum of misread numbers is still wrong.

Weeks 5, 7 · calculations in code
04Character-level errorsOne character can change the record+

What went wrong

The invoice ID INV-2024-00817 comes back as INV-2024-0817. It still looks like a real ID, so nobody notices. But now the lookup fails, or a duplicate invoice slips through.

Why it happens

The model reads text in chunks of several characters at a time. Copying a string exactly isn't really what it's built to do. It usually gets it right, but nothing guarantees it, and a dropped zero looks perfectly plausible.

How to catch it

Store IDs as text so leading zeros don't disappear, and compare them exactly in code. Check each ID against the original document or system of record, since a correctly formatted ID can still be the wrong one. Send anything that doesn't match to a person.

Spotting these failures in a polished answer is harder than reading about them. Try it yourself.

03 / TRY IT YOURSELF

Try the model.
Check the result.

Test hallucination, consistency, and math on whatever model you use.

Copy each prompt into an AI tool, write down which model you used and what it said, then open "What to look for." Everything here is public or made up, so don't swap in client information. Your results might not match a friend's, and that's fine. If the model gets it right or refuses to answer, write that down too. It still counts as a result.

Task 1: Grounding test

Copy the excerpt into your AI tool, then ask the question below.

Agreement excerpt

VENDOR SERVICES AGREEMENT (EXCERPT)
Between Northwind Facilities LLC ("Vendor") and Harbor & Pine Outfitters ("Client").
1. Services. Vendor will provide weekly cleaning services at Client's two retail locations.
2. Term. The initial term is twelve (12) months, beginning March 1, 2026.
3. Renewal. This Agreement renews automatically for successive twelve-month terms unless otherwise agreed in writing by both parties.
4. Payment. Client will pay $4,200 per month, invoiced on the first business day of each month and due within 30 days. Late payments accrue interest at 1.5% per month.
5. Price adjustments. Vendor may increase fees by up to 3% at each renewal with 60 days' written notice.
Based on this agreement, what notice period is required to cancel?

What to look for +

The correct answer is that the excerpt doesn't specify a cancellation notice period. If the model gives one, it made it up. Watch especially for it borrowing the 30 days from the payment terms or the 60 days from price adjustments; both sound plausible, and neither is about cancellation.

Design lesson: make the model point to the exact clause it's relying on, and let it say "not found."

Task 1b: Citation check

Optional: Run the prompt, then look up each paper yourself.

List three peer-reviewed academic papers, with authors, year, and journal, about using large language models to resolve retail trade deduction disputes, published before 2019.

What to look for +

Search each paper on Google Scholar. Does it exist? Are those the real authors, year, and journal? Is it actually about this topic? The prompt asks for something that almost certainly doesn't exist (modern LLMs barely existed before 2019), so invented or mismatched papers are exactly what we're looking for. Still, don't call a paper fake until you've checked.

If the model hedges or says it can't find any, that's the better outcome. Write down what actually happened.

Design lesson: Require a source for every claim, give the model a way to say "not found," and check that each source really says what it's cited for.

Task 2: Consistency check

Open a new chat for each attempt and run this prompt 5 times. Use the same model and settings each time, and write down every answer.

Classify this deduction into exactly one category (PRICING, SHORTAGE, DAMAGE, or PROMOTION). Respond with only the category. Deduction note: 'Customer deducted $2,340 citing 14 cases received crushed and short-shipped on PO 44817; promo price also not applied.'

What to look for +

Did you get the same category all five times? Look closely at the note: it describes damage, a shortage, and a pricing problem all at once, and PROMOTION is arguably right too, because of the promo price. So there's no single correct answer unless someone decides which issue wins.

That's the real lesson here. When a model flips between answers, it's often telling you the task itself is unclear. And five identical answers wouldn't have made the label right.

Design lesson: Decide the tie-breaker rule yourself, or allow more than one label. Send cases that still don't fit to a person. Otherwise, the model ends up quietly making your policy for you.

Task 3: Exact math

Try the prompt before you look at the answer. Notice whether the assistant uses a calculator tool or just answers.

What is the exact total of these amounts? $1,247.83 · $389.50 · $12,904.17 · $56.29 · $7,318.46 · $2,005.00 · $418.72 · $9,876.31 · $3,142.08 · $771.95 · $15,230.60 · $64.13 · $4,589.27 · $1,111.11 · $238.44 · $6,702.89 · $925.76 · $13,457.02 · $302.58 · $8,640.35

Then open a new chat and try it again, adding: 'Do not use any tools or code. Calculate it yourself.'

What to look for +

Correct total: $89,392.46. Check it to the cent. (We verified this total with exact decimal math.)

If the model used a code tool and got it right, that's the lesson: math belongs in code. If it got it right without a tool, nice, but you still need to check future runs. If it got it wrong and then confidently explained its wrong answer, that's exactly why you check.

Compare the two runs. If the first used a tool and got it right, and the second didn't, you've just seen the difference between the model and the tools around it.

Design lesson: Send arithmetic to code, and double-check the numbers you feed it.

So what did the probes show you? A failure tells you where a check is needed. A success tells you that one attempt worked. Neither one tells you whether a model is safe to run a client's process on its own.

Put the model into a workflow →
04 / MODELS IN WORKFLOWS

How does a model get
into a client workflow?

A model is useful when it has a clear job, the right inputs, and something checking its output.

Take accounts payable. An invoice comes in. Someone reads it, matches it to a purchase order (the company's record of what it agreed to buy), looks into anything that doesn't match, and approves the payment. An LLM can help read a messy invoice or draft an explanation of a mismatch. What it shouldn't do is quietly become the final word on how much is owed, or be the one that releases the money.

Chat, APIs, and agents change the handoff

WEEK 3

Chat

You give the model context and review what it says. For example, you paste in a made-up invoice and ask for a draft explanation of a mismatch. You're the one moving information between the model and the rest of the process.

WEEK 7

APIs

Code sends the model an input and gets an output back, with no person in between. An app could ask for the invoice fields, check them, and send problems to a review queue. The API makes the process automatic. It doesn't make it accurate.

WEEK 6

Agents

The model decides which steps to take and uses tools on its own, like looking up a purchase order. Give it limited permissions, clear points where it has to stop, and a rule that it asks for approval before doing anything that matters.

Using an LLM in a workflow doesn't make it an agent. If you already know the steps, hard-code them and let the model handle only its part. Let it choose its own steps only when that flexibility actually helps and you can check what it did. More on workflows and agents

Invoice arrives→LLM extracts fields→Code validates totals and IDs→Person reviews exceptions

Back-office work is where the stakes get real

Invoices, claims, contracts, recurring reports, and internal search are where a lot of client work lives. They mix repetitive steps with messy information, which is exactly where AI can help. How much a mistake costs depends on where the output goes. A bad draft gets edited. A bad payment, or a contract claim nobody verified, can do real damage.

For every step, ask three questions. What counts as correct? What happens if it's wrong? Who or what checks it? And "a human will check it" isn't a plan yet. Who checks? What do they see? Can they actually stop the payment?

Model families from Week 1 +

Closed families: Claude (Anthropic), GPT (OpenAI), and Gemini (Google).

Families with open-weight releases: Qwen (Alibaba), DeepSeek, Kimi (Moonshot), Llama (Meta), and Mistral.

You might choose a model from these companies. You still need a plan for how to use it. Test the specific model on real examples of your task, and think about permissions, hosting, cost, speed, and licensing. Also, open weights don't automatically mean you can use a model however you want, or that your data stays private.

This list comes from the lesson. Check current releases when you choose a model, because what's available changes often.

Think in steps. Break the process apart, decide who handles each one, and attach a check before its output moves on.

CONFIDENTIALITY / BEFORE YOUR DELIVERABLE

Public, synthetic, or fully anonymized.

Your portfolio pieces can only use public, synthetic (made-up), or fully anonymized material. That means no client names, data, or documents, ever. And never paste client data into a consumer AI tool like ChatGPT or Claude. Stick to invented companies, public datasets, and made-up examples.

Taking out the company name usually isn't enough, because other details can still give it away. The easiest move is to invent the workflow from scratch.

Full example: invoice matching at Hearthstone +

Hearthstone Home Goods is a made-up retailer. Its accounts payable team matches about 800 vendor invoices a month to purchase orders before paying them.

SubtaskApproachReasoning and alternatives
Pull vendor, invoice number, line items, and total from PDFsCombinationAn LLM can read invoices in all kinds of layouts. Code then checks that the required fields are there, the IDs look right, and the totals add up.

Why not something else? A fixed template breaks on layouts it hasn't seen. An LLM on its own might misread or invent a field, so anything missing or inconsistent goes to review.

Match vendor names to the vendor listCombinationFuzzy-matching code (which finds close-but-not-exact matches) suggests candidates, an LLM helps with the tricky ones, and a person confirms anything still unresolved.

Why not something else? Exact matching misses abbreviations like "Acme Corp." vs. "Acme Corporation." An LLM on its own might merge two different vendors. The approved vendor list is always the reference.

Compare invoice totals to PO amountsRules / codeRead the amounts as exact decimals (or whole cents) and compare them with a clear rule.

Why not something else? An LLM adds uncertainty to exact math. A person doesn't need to redo routine matches, only the misreads and approved exceptions.

Flag possible duplicate invoicesRules / codeFlag any invoices with the same number, vendor, and amount. It's simple and easy to test. Flag them for review rather than deleting them.

Why not something else? An LLM's sense of "these look similar" is hard to reproduce. But this rule also misses duplicates where the ID or amount was changed, so near-duplicates need a separate check.

Explain each mismatch in plain EnglishLLMThe LLM drafts from the verified fields and the known reason for the mismatch, and someone reviews it before it's sent.

Why not something else? Templates work for fixed messages but read awkwardly when every case is different. The LLM might invent a reason, so it has to stick to the facts it's given. This covers drafting only, not sending on its own.

Approve payment on mismatches over $5,000HumanAn authorized person looks at the source records and owns the decision.

Why not something else? Code can enforce the $5,000 threshold, and an LLM can summarize the case, but neither should approve the payment on its own.

Biggest risk

The model reads $12,450 as $1,245, and the wrong payment goes out. The safeguard: code re-adds the line items and sends any disagreement to a review queue. The reviewer sees the original invoice, what was extracted, the purchase order, and which check failed. Nothing gets paid until an authorized person sorts it out.

One catch: if the total and the line items are misread in the same way, the math can still check out. That's why someone should also spot-check the source documents.

Write for an executive who needs to know whether this process can be trusted. "Use AI for invoices" is too vague. "An LLM reads the invoices, code checks the amounts, and a named reviewer handles exceptions before anything is paid" tells them what they're getting and how it's controlled.

07 / THE TAKEAWAY

What should AI do,
and what shouldn’t it?

Use an LLM when reading or writing language helps. Use code when there's an exact rule and one right answer. Put a person wherever a decision needs judgment or someone to be accountable.

Most good workflows use all three. Treat what the model gives you as a draft to check, never as permission to act. A solid design names what could go wrong, checks it against something independent, and spells out what happens when the check fails. That's how a tool that writes plausible text becomes something a client can depend on.

Check your understanding

1. An answer is fluent and includes a citation. Is it verified? +

No. Open the source and make sure it actually supports that specific claim. Real sources get cited for things they never said, and fake citations can look completely real.

2. A model gets the same invoice total right three times. Can it own the calculation? +

No. Three right answers don't mean the fourth will be right. Let code do the math from checked amounts, and send mismatches to a reviewer. If the assistant used a calculator, remember that the calculator did the math. The model still read the numbers, and that step can go wrong.

3. An API returns a valid invoice record. What's still missing? +

Proof that the values are right. A neatly formatted record can still contain the wrong numbers. Check IDs and amounts against the source, make sure the required fields are there, and decide what happens when something doesn't match.

4. Why is "a human checks it" an incomplete defense? +

Because it skips the details. Which cases get reviewed? Who reviews them? What evidence do they see? Can they stop the next step? Without those answers, the reviewer might only see a convincing summary and never the mistake hidden inside it.

Take this into Week 2: figure out what the client is actually trying to achieve before you decide what to automate. Start with one real workflow and ask what "done right" looks like at each step.
